# 抢购程序通用经验

这份文档汇总了所有抢购程序（NexKr 2026 国庆、NewNB 2026-10 沪港 CM、FAC 2026-11）共同的
规矩和踩过的坑。写新的抢购程序，或给新活动重启旧程序之前，先读一遍。各站点自己的细节在
README 的“抢购程序：重新开抢与踩过的坑”一节。

## 1. 只买已经公开的链接（用户定的规矩）

- **隐藏链接只通知，不下单。** 监控发现的隐藏商品或分类（外面搜不到、商城菜单里没有、
  TG 也还没发），只用来通知用户、提前做好准备。在它公开之前，不要以登录状态去打开，也不要下单。
- **原因**：商品还没公开就下了单，商家客服如果来问“你是怎么找到这个链接的”，很难回答，
  看起来也像在扫站，容易触发风控、连累账号。
- **流程**（FAC 已实现，其他站照做）：
  1. 监控发现隐藏页面或商品：发通知，标记为“未公开”。
  2. 之后每 2 分钟看一次商城的公开菜单或公开列表（不登录访问隐藏页面），同时等 TG 推送。
  3. 链接出现在公开菜单或列表里，或者商家在 TG 发了这个链接：才算公开。
  4. 链接至少公开满 3–5 秒才下单，从“它可能刚公开的那一刻”算起：TG 发出来说明已经公开，马上下单；
     定时检查发现已公开时，一般早就过了这几秒（上次检查在几分钟前），也马上下单；只有上一次检查
     （当时还没公开）就在几秒前，才补足剩下的秒数。
- **公开的判断标准**：商家在 TG 频道或群里发了链接，或者链接出现在商城自己的菜单或公开列表里。
  NexKr 和 NewNB 两次抢购都是在公开目录（NexKr 商品 API、NewNB 节点列表）里看到有货才下的单。
- **链接至少公开 3–5 秒后再下单**（FAC 用 4 秒），看起来像真人反应，不容易触发风控；但不能多等，
  否则会被别人抢走。已经公开够久的（TG 已发、定时检查才看到）就马上下单。浏览器、登录这些准备
  工作提前做好。
- 刚出现就秒下也有坑：NewNB 第一次买到的是管理员的测试节点，几分钟后被终止退款。抢到后要去
  面板确认服务正常开通。

## 2. 测试

- **测试单只能下在公开在售的正价商品上**，不能用隐藏链接。隐藏商品外面搜不到，在上面下单太
  显眼（2026-11-08 在 FAC 的隐藏商品 TW-MobileData 上下过一次测试单，已取消，以后不再这样做）。
- 如果所有公开商品都售罄，就等补货再测，并告诉用户；不要拿隐藏链接代替。
- 测试单保证付不了款：要么余额低于总价（FAC 程序会先读余额再点结账），要么用 `--dry-run`
  停在下单前。测试完马上取消或删除订单。
- 先用 `--dry-run` / `--login-only` / `--check-login` 这类只读模式验证，再做会下单的测试。

## 3. 下单前必须确认

- **点到下单页**，看真实价格、付款周期、配置项，以及按钮是否可用（列表价不可信，见 README
  “接入或排查站点：必须点到下单页”）。
- 设**价格上限**，超价只通知、不下单。按“今日总价”算，要含安装费。
- 按**名称、关键词过滤**（例如 FAC 只买名称含 SeedNet、不是 NAT、年付的商品）。不符合的
  直接放弃这个链接，别反复刷。
- **只买一次**：成功后写标记文件并暂停，要在 TG `/autobuy` 里恢复才会再买。

## 4. 登录与人机验证

- 能用账号密码自动登录就用；登录信息放在 `data/<站点>_account.env`（0600，不进 git）。
- Cloudflare Turnstile：Playwright 启动的 Chromium，再加伪造的 UA，会被当场判失败。直接启动
  一个普通 Chromium（真实 UA、没有自动化参数），只通过 127.0.0.1 的 CDP 端口去控制，就能自动
  通过。不要监听浏览器 console。
- reCAPTCHA v3（NexKr）：headed Chromium 加 xvfb 能拿到分数。
- 关浏览器走 CDP `Browser.close`，别 `kill` 整个进程组，否则刚写的 cookie 会丢。
- 搞清楚会话能活多久（FAC：会话 2 小时，“记住我” 30 天），按这个间隔检查登录状态，不用几分钟
  就去“活动”一次。用户点“退出登录”可能让所有设备的“记住我”一起失效，程序要能自己重新登录。
- 程序自己重新登录可能把用户挤下线（NexKr）；需要用户手动操作时，程序要停止自动登录。

## 5. 付款

- 余额付款最快。提前充值，并留意同账号的续费账单会不会先把余额用掉（例如 FAC #210 在 11-22 续费）。
- 余额不够时保留未付订单，并在 TG 发付款链接（NexKr、NewNB、FAC 都是这样）。
- 订单建好但没付清时，先发 TG 让用户能上去手动付，再让程序自己试着付款，最后发付款结果
  （用户 2026-11-09 定的）。
- 网站默认的付款选项，非必要不要改（FAC 改 `use_credits` 会让结账卡住）。

## 6. 失败与重试

- 下单失败要发 TG，并附上商品链接，用户可以马上手动去买。
- 结账请求可能不回：先去订单或账单列表看有没有新单，再决定是否重试，**绝不能重复下单**
  （FAC 最多等 90 秒，然后查 `/invoices`）。
- 结账卡住要马上通知用户，不要等程序自己超时（FAC：20 秒没回应就发 TG），让用户可以手动接手；
  消息里提醒用户先看账单页，有新账单就付那张，别再下一单。
- 不要无脑重试：NexKr 曾在全部售罄的区域上两天打出约 1.17 万个 409。只在有货的选项上下单，
  同一个链接失败几次就放弃。
- 优惠码：一个被拒可能让整单失败（NexKr `coupon_rejected`），要预检，失败了就去掉重下。

## 7. 对网站要礼貌（全局规矩）

- 同一个站点一次只发一个请求，页面之间至少隔 3–5 秒；只有和用户约定好的抢购目标可以加快，
  而且只针对那一个链接。
- 遇到 403、429、验证页，立即停下，退避至少 30 分钟并通知用户，不要死循环重试。
- 能用推送（TG）唤醒就不要轮询；平时不开浏览器。

## 8. 运维

- 抢购程序作为独立的 systemd 服务或临时 unit 运行，带内存上限。抢完以后：停掉服务，删除账号
  文件和 cookie，提醒用户改密码。**代码和经验都保留**，下次活动接着用。
- SSH 命令被中断后，远端进程可能还在跑。中断后要检查，并停掉残留的进程（2026-11-08 有一个
  被叫停的测试脚本在生产机上继续跑，往购物车里加了商品）。
- 改动生产机之前先备份，部署后检查服务状态和日志。
