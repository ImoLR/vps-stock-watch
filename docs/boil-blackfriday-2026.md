时间线、现有程序为什么没买、讨论过的黑五专用抢购设计，以及能用到 SeedNet / 日本 / 美国抢购上的经验。

**状态**：盲盒不买，盲盒专用的抢购没有做。用户倾向在群里或 NodeSeek 收美国（ATT / Frontier）和
日本（SoftBank）的奖品。第 4 节的设计留着，以后 BOIL 再出整点放货的活动时可以照做。

**已经做进 SeedNet / 日美抢购的部分（2026-11-26，用户同意）**：整点冲刺，只在公开的 festive-offer

预告出来时活动分组已经在了，监控看到分组就够。详见 README 的 BOIL 抢购程序一节。

## 3. 现有程序为什么没买（按设计）

下面三条，任何一条单独都会拦下：
- `name_exclude` 里有「盲盒」；
- 文字里没有「動態」，过不了动态 IPv4 规则；
- 「$111 月繳」按月算超过所有价格上限。

**如果它是目标**：从发帖到建单大约 14 秒，大部分花在下面这几步：
- TG 唤醒，晚 5 秒；
- 加购物车、提交配置、打开结账页，每步之间隔 1.5 秒；
- 结账前读账单列表，这一步按普通翻页间隔，要等 4 秒；
- 最后提交结账。

9 份、约 1 分钟卖完，14 秒有比较大的机会，但不保证。

## 4. 黑五专用设计（讨论定稿，未实施）

和 SeedNet / 日本 / 美国的目标完全分开：单独的规则、单独的完成标记，到期后自动失效。两边唯一
共用的是账户余额。

1. **条件**：名称有 盲盒 / luckybox，说明里同时有 SoftBank、ATT（或 AT&T）、Frontier；今日总价 ≤ $111；
   余额付清；只买 1 个；不用优惠码；不套用动态 IPv4 规则和「盲盒」排除词。
2. **公开就直接买**：festive-offer 在侧栏里就是公开的，看到有货马上下单，不等 TG，也不等 3–5 秒。
   TG 帖一到也马上下单。
3. **整点冲刺**（主力）：活动当天白天每个整点（台湾 08:00–20:00，即 JST 09:00–21:00，13 次），
   整点前 30 秒到整点后 60 秒，每 3 秒看一次 festive-offer 公开页（每次约 30 个请求）。整点前 1 分钟
   先确认登录、清空购物车、预读账单号。半点（:30）要不要加，用户还没定（加了约多 400 个请求）。
4. **预告加速**：频道或官方账号发的帖子里有「黑五 / 盲盒 / 抢购 / 開賣 / 特賣」，即使没链接，也进入准备：
   登录待命，页面改成每 5 秒一次，最长 20 分钟；帖子写了时间，就在那个时间前后改成每 2 秒。
   需要改 `fac_tg_watch`：现在没链接的帖子不会唤醒抢购程序。
5. **兜底**：页面照常每 60 秒一次，TG 带链接的帖约 5 秒唤醒。
6. **提速**：账单号在待命时预读（省 4 秒），下单几步之间隔 1 秒，预计从放货到建单 4–5 秒。
7. **结账失败**（库存不足）：发 TG，回到冲刺看还有没有货，不连续重试。
8. **请求量**：冲刺约 390 + 预告最多约 240 + 兜底约 1.4k，当天约 2k，只限这一天。冲刺只看
   festive-offer 这一个页面（约定的抢购目标）；403 / 429 / 验证页立即停 30 分钟并通知。

## 5. 能用到 SeedNet / 日本 / 美国抢购上的经验

`boil_autobuy` 的 SeedNet、日美两个目标同样只看 festive-offer + TG，下面几条照样适用：

- **BOIL 是整点放货的**，而且会先挂 0 库存的卡。圣诞 / 新春的生肖款很可能也一样。可以加两条规则：
  一是「festive-offer 上出现符合目标、但还是 0 库存的卡」时，进入冲刺；二是预告帖出现时提前进入准备。
  光靠 TG（晚约 5 秒）和每 20–60 秒一次的页面轮询，会比守着页面的人慢。
- **账单号预读、下单间隔 1 秒**：两个目标都能用，从 14 秒左右压到 8 秒左右。
- **链接 slug 不可靠**：TG 链接带随机后缀，和卡片的不一样。现在程序按 PID / 配置页里的名称识别，
  不认 slug，这样是对的，以后也别改成按 slug 匹配。
- **只卖完、不下架的卡片会一直把程序挂在待命状态**：festive-offer 有卡（哪怕 0 库存），`boilcloud_sale`
  每 5 分钟就会触发一次；卡片文字里有「日本 / 美國」，就会一直武装，程序每 60 秒查一次
  （约 1.4k 请求/天）。当时觉得在预算内没改，**第二天 AWS 的 IP 就因此被拉黑了**，见第 6 节（已改）。
- **预告帖会被删**：转发记录里只存了摘要。以后可以把官方帖的发帖时间和前 200 字写进日志，复盘时才有依据。
- **BOIL 还没真正付过一次款**：余额付款、完成标记和成功通知这条路至今只做过 dry run 和不勾服务条款的测试。
  SeedNet 开卖前最好找一个公开的正价商品真付一次（便宜、能退的），先把这条路跑通。
- **Telethon 偶尔报 `PersistentTimestampOutdatedError`**（当晚 22:53、23:03 都有），推送可能变慢。
  预告出现后，可以额外每 2–3 秒拉一次频道最新一条消息，作为保险。
- 「續費同價」这类活动价，转让以后续费价还算不算，要先问商家；它决定二手价值。

## 6. 11-27 AWS 的 IP 被 BOIL 拉黑（复盘）

**原因**：盲盒卡的说明里写着 SeedNet、日本等奖品。旧规则只看 festive-offer 的卡片文字里有没有目标词，
所以监控每 5 分钟就把抢购程序重新武装一次，每次往后延 6 小时。抢购程序就一直每 60 秒刷一次活动页，
可页面上从头到尾没有一张卡是我们要买的（日志一直是 `1 cards, 0 matching`）。加上监控自己的请求，
一天约 1700 次，平均每分钟一次多，连续了约 18 小时。黑五期间 BOIL 收紧了防护，就被拦了。

| 时间（台湾） | 事件 |
|---|---|
| 11-26 22:59 | 监控看到 festive-offer 挂出盲盒卡，唤醒抢购程序；之后每 5 分钟续一次 |
| 11-26 23:00 – 11-27 16:43 | 抢购程序每 60 秒刷一次活动页（24 小时内约 1160 次） |
| 16:30 – 16:34 | 活动页清空（0 张卡）；监控发出「活动页关闭」提醒，用户在 TG 看到 |
| 16:43:06 | 最后一次正常 |
| 16:44:06 | 抢购程序拿到 403，Cloudflare 的「Attention Required」拦截页；16:44:36 监控也 403 |
| 16:46:12 | BOIL 频道发了新一轮盲盒链接（`luckybox-120e552c`）。抢购程序被唤醒，登录拿到 403，**进程崩溃**，1 分钟后被 systemd 重启 |
| 16:5x | 开发机同一个请求返回 200，确认只是 AWS 的 IP（43.199.143.188）被拉黑 |
| 17:04 | 修复上线，监控通过 TCS SeedNet 隧道正常读到页面 |

**损失**：这一轮新盲盒本来就不是目标，没错过要买的东西。但如果被拦的这段时间 BOIL 发的是 SeedNet，就下不了单。

**放货规律补充**：这一轮是先清空活动页（约 16:30），十几分钟后（16:46）才在 TG 发新链接，**不是整点放货**。
「活动页关了」是准备信号，但这次放货时间不在整点冲刺的窗口里。整点冲刺只在出现符合目标的 0 库存卡时才启动，
所以保留不动；TG 唤醒照样会马上下单。

**改动**（用户 2026-11-27 同意）：
1. 监控的触发里带上每张卡各自的文字（`cards`）。抢购程序只在**有一张卡完全符合还没买到的目标**时才武装，
   判断规则和下单一样（动态 IPv4，非盲盒、非 NAT，等等）；只被监控武装的活动页，看一次没有目标卡就解除武装。
2. 轮询节奏：前 10 分钟每 20 秒一次，之后每 5 分钟一次（以前是前 30 分钟每 20 秒、之后每 60 秒）。
3. 遇到 403 / 429 / 验证页：60 分钟内完全不访问 BOIL，期间新来的链接也等着。登录检查遇到 403 不再让进程崩溃。
4. 出口：抢购程序和监控都走 `boil-egress.service`（SSH -D 127.0.0.1:1082，到 TCS SeedNet
   `tcsseednet.imgamer.top`，当时的 IP 是 123.204.9.229）。那边是动态 IP，被拉黑了可以换；给它的 key 只能转发到
   `cloud.boil.network:443`，不能开 shell。AWS 的 IP 先不用，等它自己解封。

**同日第二轮改动（用户 2026-11-27）**：BOIL 第二弹的帖子（717 号，16:58 补了 AI 总结）写着：9 份 33 秒卖完，
首单到末单 13 秒；开卖瞬间 20 多人进场；「已拦截脚本刷新与直链下单 370+ 次」。我们以前的做法两条都占：
刷新是带着登录状态刷的，下单用的是 `cart.php?a=add&pid=N`。所以改成：
- **刷新线不登录**：监控、抢购程序看活动页、整点冲刺都用不登录的会话。
- **购买线登录**：先打开活动页，再点卡片自己的「立即購買」（带 Referer），或者打开 TG 帖里的链接。
  TG 链接就是卡片按钮的地址，不算直链；用户手动点时看到报错，是因为已经卖完了，页面显示「缺貨中」。
- **TG 链接缺货时冲刺**：可能是目标时，每 1 秒再开一次，最多 60 秒。
- **出口**：优先 TCS SeedNet；隧道不通就改 AWS 直连。被 403 就停 60 分钟，不换 IP 硬冲（建议，待用户确认）。
  TCS 换 IP 要约 30 秒（11-25 实测），比一场盲盒卖完还慢，而且会断 FLVX 落地机上的用户连接。
- **AWS 的 IP**：17:30 再测已经解封，前后约 46 分钟。
- **17:38 新发现**：在公开正价商品（HKT 300M）上做 dry run。登录、读余额都正常，接着直接 GET `cart.php?a=empty` 拿到 403。
  同一时间监控读活动页正常，17:42 那轮也正常，所以 IP 没有被整个封掉，是这个网址被拦了：浏览器不会自己打开它，
  页面上的「清空購物車」是表单提交。之后清空购物车改成「打开购物车页 → 有东西才提交它的表单」，下单每一步都按页面顺序走
  （配置 → 购物车页 → 结账），带上一页作 Referer，POST 带 Origin。用户的判断：照正常路径点进去应该不会碰到 403。
  这能大幅降低被拦的概率，但不保证：我们是纯 HTTP，不跑 JS，如果结账加了人机验证（Turnstile）就过不去。

**18:11–19:02 再发现（Cloudflare 验证）**：18:11 连普通的购物车页 `cart.php?a=view` 也 403。18:46 不登录的纯 HTTP 同样 403，
标题「Just a moment...」，`cf-mitigated: challenge`，说明是 Cloudflare 的浏览器验证，不是账号被标记。
用 Chromium 打开一开始卡住，截图显示连不上 `challenges.cloudflare.com`：隧道的 key 只放行了 BOIL。放行它之后要重启隧道
（key 的限制只在登录时读）。之后 Chromium 12–22 秒自动通过。纯 HTTP 带上它的 `cf_clearance`、同一个 UA、同一个 IP 也能进购物车。
所以采用混合方案：浏览器只负责续通行证，下单还是纯 HTTP。
18:56 抢购程序第一次自己续通行证时，把验证通过后的跳转误判成失败，按拦截处理，并给用户发了一条「疑似被网站限流」，**这条是误报**。
18:57 修好（等到拿到 cookie 且标题出现 BOILCLOUD 才算通过），15 秒续上。
18:59 在公开正价商品 HKT 300M 上做完整 dry run：卡片链接 → 配置 → 购物车页 → 结账页（今日总价 $66）→ 用表单清空购物车，
每一步都是 200，没有下单。
同时上线 TG 警戒窗口（见 README）。用户 2026-11-27 的判断：照正常路径点进去，加上浏览器通行证，应该不会再碰到 403。

**20:00 前后（付款规则，用户）**：BOIL 付款时才扣库存，付了款也可能没机器（之前抽奖活动遇到过），以 BOIL 的确认邮件为准。
抢购程序改成：余额付不了就不下单；没付清不算买到（继续抢）；付了款记成「已付款，待确认」，之后查账单和服务状态，
被退款或取消就自动恢复继续抢。日美要给 SeedNet 留 $342。通行证实测 30 分钟失效，改成到期前续。
