# 抢购程序通用经验

这份文档汇总了所有抢购程序（NexKr 2026 国庆、NewNB 2026-10 沪港 CM、FAC 2026-11、BOIL 2026-11）共同的
规矩和踩过的坑。写新的抢购程序，或给新活动重启旧程序之前，先读一遍。各站点自己的细节在
README 的“抢购程序：重新开抢与踩过的坑”一节。

## 1. 只买已经公开的链接（用户定的规矩）

- **隐藏链接只通知，不下单。** 监控发现的隐藏商品或分类（外面搜不到、商城菜单里没有、
  TG 也还没发），只用来通知用户、提前做好准备。在它公开之前，不要以登录状态去打开，也不要下单。
- **原因**：商品还没公开就下了单，商家客服如果来问“你是怎么找到这个链接的”，很难回答，
  看起来也像在扫站，容易触发风控、连累账号。
- **流程**（FAC 已实现，其他站照做）：
  1. 监控发现隐藏页面或商品：发通知，标记为“未公开”。
  2. 之后每 2 分钟看一次商城的公开菜单或公开列表（不登录访问隐藏页面），同时等 TG 推送。
  3. 链接出现在公开菜单或列表里，或者商家在 TG 发了这个链接：才算公开。
  4. 链接至少公开满 3–5 秒才下单，从“它可能刚公开的那一刻”算起：TG 发出来说明已经公开，马上下单；
     定时检查发现已公开时，一般早就过了这几秒（上次检查在几分钟前），也马上下单；只有上一次检查
     （当时还没公开）就在几秒前，才补足剩下的秒数。
- **公开的判断标准**：商家在 TG 频道或群里发了链接，或者链接出现在商城自己的菜单或公开列表里。
  NexKr 和 NewNB 两次抢购都是在公开目录（NexKr 商品 API、NewNB 节点列表）里看到有货才下的单。
- **链接至少公开 3–5 秒后再下单**（FAC 用 4 秒），看起来像真人反应，不容易触发风控；但不能多等，
  否则会被别人抢走。已经公开够久的（TG 已发、定时检查才看到）就马上下单。浏览器、登录这些准备
  工作提前做好。
- 刚出现就秒下也有坑：NewNB 第一次买到的是管理员的测试节点，几分钟后被终止退款。抢到后要去
  面板确认服务正常开通。

## 2. 测试

- **测试单只能下在公开在售的正价商品上**，不能用隐藏链接。隐藏商品外面搜不到，在上面下单太
  显眼（2026-11-08 在 FAC 的隐藏商品 TW-MobileData 上下过一次测试单，已取消，以后不再这样做）。
- 如果所有公开商品都售罄，就等补货再测，并告诉用户；不要拿隐藏链接代替。
- 测试单保证付不了款：要么余额低于总价（FAC 程序会先读余额再点结账），要么用 `--dry-run`
  停在下单前。测试完马上取消或删除订单。
- 先用 `--dry-run` / `--login-only` / `--check-login` 这类只读模式验证，再做会下单的测试。
- WHMCS 站（BOIL）可以不建单就测到最后一步：照常提交结账，但不勾服务条款，WHMCS 会回“您必須同意我們的
  服務條款”，不建订单（`--tos-probe-url`）。测完去服务和账单列表确认没有新增。

## 3. 下单前必须确认

- **点到下单页**，看真实价格、付款周期、配置项，以及按钮是否可用（列表价不可信，见 README
  “接入或排查站点：必须点到下单页”）。
- 设**价格上限**，超价只通知、不下单。按“今日总价”算，要含安装费。
- 按**名称、关键词过滤**（例如 FAC 只买名称含 SeedNet、不是 NAT、年付的商品）。不符合的
  直接放弃这个链接，别反复刷。
- 用户的价格规则常常是“折合每月”（BOIL 2026-11-24：SeedNet ≤ $28.5/月，日美只有年付 ≤ $40/月、
  多周期 < $30/月）：按今日总价 ÷ 周期月数算，区分“只有年付”和“多周期”两档；“动态”这类要求要认
  商家原文里的词（“動態”），并留意“靜態IPv4・動態IPv6”“動態 IP「CGNAT」”这种半真半假的写法。
- 商品直链不一定带 ID：BOIL 的 `/store/<分组>/<商品>` 直接跳到配置页，网址里没有 PID。别靠“先解析出
  ID 再下单”，解析失败会把真正的目标悄悄丢掉；用一个真实直链跑一次 dry run 验证。
- **只买一次**：成功后写标记文件并暂停，要在 TG `/autobuy` 里恢复才会再买。

## 3a. 商家怎么放货（BOIL 2026 黑五，详见 `docs/boil-blackfriday-2026.md`）

- 顺序是：预告帖（约提前 9 分钟，事后删掉）→ 活动分组公开，挂出 **0 库存**的卡（提前 1–6 分钟）→
  带链接的正式帖（提前约 2 秒）→ **整点放货**（0:00 JST）→ 9 份约 1 分钟卖完。
- 公开分组里出现目标卡，哪怕是 0 库存，也说明快开卖了：围着下一个整点冲刺（整点前 30 秒到后
  60 秒每 3 秒一次，只看这一个页面）。光靠 TG（晚约 5 秒）和每分钟一次的轮询，会比守着页面的人慢。
- 下单之前的准备（登录、清空购物车、预读账单号）都在放货前做完，放货后只剩三四个请求。

## 4. 登录与人机验证

- 能用账号密码自动登录就用；登录信息放在 `data/<站点>_account.env`（0600，不进 git）。
- Cloudflare Turnstile：Playwright 启动的 Chromium，再加伪造的 UA，会被当场判失败。直接启动
  一个普通 Chromium（真实 UA、没有自动化参数），只通过 127.0.0.1 的 CDP 端口去控制，就能自动
  通过。不要监听浏览器 console。
- reCAPTCHA v3（NexKr）：headed Chromium 加 xvfb 能拿到分数。
- 关浏览器走 CDP `Browser.close`，别 `kill` 整个进程组，否则刚写的 cookie 会丢。
- 搞清楚会话能活多久（FAC：会话 2 小时，“记住我” 30 天），按这个间隔检查登录状态，不用几分钟
  就去“活动”一次。用户点“退出登录”可能让所有设备的“记住我”一起失效，程序要能自己重新登录。
- 程序自己重新登录可能把用户挤下线（NexKr）；需要用户手动操作时，程序要停止自动登录。

## 4a. 两种过验证、保持登录的做法：FAC（全程浏览器）和 BOIL（浏览器拿通行证 + HTTP 下单）

2026-11 两个站点各用了一种，以后遇到新站点，先看验证挂在哪里，再选做法。

| | FAC（fachost.cloud，Paymenter） | BOIL（cloud.boil.network，WHMCS） |
|---|---|---|
| 验证在哪 | Cloudflare **Turnstile 挂在登录和结账两个动作上**，每次都要当场过 | 2026-11-27 起 **cart.php 整块挂 Cloudflare 托管验证**（「Just a moment」），过一次发一张 `cf_clearance` |
| 怎么过 | 单独启动的普通 Chromium（不用 Playwright 启动、不加自动化参数），只通过 CDP 控制，Turnstile 自己通过 | 同样的普通 Chromium 打开一次 cart.php 拿到 `cf_clearance`，再把它和浏览器的 UA 交给 HTTP 会话 |
| 下单 | **全程浏览器**（每个动作都要验证，HTTP 走不通） | **纯 HTTP**：带着通行证，同一 IP、同一 UA，验证不会再拦。每步一个请求，网站卡时比浏览器稳得多 |
| 保持状态 | 登录存在浏览器 profile 里（会话 2 小时，「记住我」30 天）；每 6 小时开一次浏览器查登录，查完就关 | 通行证实测 30 分钟有效：平时满 27 分钟续，有活动迹象时满 20 分钟续；续一次在 8 核新机器约 7 秒，在 1 GB 内存的 AWS 上 16–64 秒 |
| 抢购时遇到验证 | 正常流程，浏览器当场过 | 当场重新认证（约 7 秒），然后继续用 HTTP 下单。**不要切成浏览器下单**（用户 2026-11-28：网站卡的时候浏览器连页面都打不开，大家都要重新认证，比的是谁先认证完） |
| 内存 | 抢购时 Chromium 约 500 MB | 续通行证时 Chromium 峰值约 700 MB，平时纯 HTTP 几十 MB |

**怎么选**：

- 验证只挂在登录、结账这类**动作**上（Turnstile 组件嵌在表单里）：走 FAC 的做法，全程浏览器，浏览器只在要动作时开。
- 验证挂在**整页**上（打开就是「Just a moment」，响应头 `cf-mitigated: challenge`），而且过了以后会发 `cf_clearance`：走 BOIL 的做法，浏览器只负责续通行证，下单用 HTTP。
- 两种都先**不登录**测一次，分清是验证还是账号被封。

**BOIL 这种做法的前提**（任何一条变了，通行证就失效，要重新认证）：

1. **同一个出口 IP**：浏览器和 HTTP 都走同一条隧道。Chromium 用 PAC 只把目标站和 `challenges.cloudflare.com` 交给隧道，隧道的 key 两个都要放行。
2. **同一个 UA**：Chrome 实际发的是简化过的 `Chrome/<主版本>.0.0.0`，要从页面里读 `navigator.userAgent`，不能自己编。换机器时要装同一个 Chromium 版本（Playwright 同一个 build），旧通行证才能接着用（2026-11-28 搬机器时验证过）。
3. **没过期**：续之前先删掉 profile 里旧的 `cf_clearance`，否则 Cloudflare 直接放行，「续」到的还是那张旧的，到点照样失效（2026-11-27 踩过）。
4. **出口 IP 换了**：通行证跟着作废。TCS SeedNet 每天 04:00 换 IP，所以 BOIL 夜里干脆暂停（见 §4b），早上重新认证。

**还没验证过的风险**：活动中途商家调高验证等级（BOIL 在 2026-11-27 黑五当天加过一次验证），旧通行证可能不认。程序会先重新认证一次，还不行就停 60 分钟，并把链接发给用户手动买。

## 4b. 夜间暂停（`quiet_hours`）

- 2026-11-28 起（用户定的）：台湾时间 **00:05–09:05**，BOIL 的监控和抢购程序、FAC 的活动页监控都**不访问网站**；FAC 抢购程序这段时间不查登录。理由：夜里不会有活动，也不会发公告；TCS SeedNet 04:00 换 IP 也正好落在这段时间里。
- TG 转发照常 24 小时运行，商家发帖照样通知用户。BOIL 抢购程序夜里**丢掉** TG 触发（优惠码照样记下来，这一步不访问网站）；FAC 抢购程序夜里仍然会被 TG 链接唤醒（每 6 小时才开一次浏览器，省不了多少，错过 FAC 的活动代价更大）。
- 09:05 BOIL 只做两件事：重新认证、查一次登录。**不跑下单流程，不加购物车**（用户：老是加了又取消不好）。之后照常每 20–27 分钟续一次。FAC 在 09:05 查一次登录。
- 补货监控（NexKr、NNB、VMSILO、力群、DMIT、Misaka）**不暂停**：夜里也会有人退订或自动补货；它们在新机器上一共才几十 MB 内存。
- 配置：在 provider 或抢购程序的配置里写 `quiet_hours: "00:05-09:05"`（台湾时间，不受主机时区影响；可以跨午夜；空字符串表示关闭；写错了程序启动时就会报错）。实现在 `watcher/quiet_hours.py`。

## 5. 付款

- 余额付款最快。提前充值，并留意同账号的续费账单会不会先把余额用掉（例如 FAC #210 在 11-22 续费）。
- 余额不够时保留未付订单，并在 TG 发付款链接（NexKr、NewNB、FAC 都是这样）。
- 订单建好但没付清时，先发 TG 让用户能上去手动付，再让程序自己试着付款，最后发付款结果
  （用户 2026-11-09 定的）。
- 网站默认的付款选项，非必要不要改（FAC 改 `use_credits` 会让结账卡住）。

- **先弄清商家什么时候扣库存**（BOIL：付款时才扣，付了款也可能被退款）：这种商家下单不算买到，要在同一次结账里
  用余额付清；付款成功后还要再查订单是否开通、有没有被退款，被退款就继续抢。余额要提前充够，余额不够就别下单。

## 6. 失败与重试

- 下单失败要发 TG，并附上商品链接，用户可以马上手动去买。
- 结账请求可能不回：先去订单或账单列表看有没有新单，再决定是否重试，**绝不能重复下单**
  （FAC 最多等 90 秒，然后查 `/invoices`）。
- 结账卡住要马上通知用户，不要等程序自己超时（FAC：20 秒没回应就发 TG），让用户可以手动接手；
  消息里提醒用户先看账单页，有新账单就付那张，别再下一单。
- 不要无脑重试：NexKr 曾在全部售罄的区域上两天打出约 1.17 万个 409。只在有货的选项上下单，
  同一个链接失败几次就放弃。
- 优惠码：一个被拒可能让整单失败（NexKr `coupon_rejected`），要预检，失败了就去掉重下。

## 7. 对网站要礼貌（全局规矩）

- 同一个站点一次只发一个请求，页面之间至少隔 3–5 秒；只有和用户约定好的抢购目标可以加快，
  而且只针对那一个链接。
- 遇到 403、429、验证页，立即停下，退避至少 30 分钟并通知用户，不要死循环重试。
- 能用推送（TG）唤醒就不要轮询；平时不开浏览器。
- **监控唤醒抢购程序，要用和下单一样的完整规则逐张卡判断，不能只看关键词**（BOIL 2026-11-27：
  盲盒说明里写着 SeedNet 奖品，抢购程序被一直续着，每 60 秒刷一次，刷了 18 小时，AWS 的 IP 被
  Cloudflare 拉黑。详见 `docs/boil-blackfriday-2026.md` 第 6 节）。监控已经在定时读的页面，抢购程序
  不要再重复读；没有要买的东西就把页面交回监控。
- 算请求量要把同一站点的所有程序加起来（监控 + 抢购 + 冲刺）。「在预算内」不等于安全：持续十几个小时、
  每分钟一次的请求，在活动期间很容易被拦。
- 403 要在每一条请求路径上都处理（包括登录检查），被拦以后整个程序都要停，不能崩溃重启了又去打。
- **刷新和购买分两条线**：刷新（轮询、冲刺）不登录，登录状态只用来下单；下单走页面上的按钮链接或商家发出来的链接，
  带上来源页，不要直接拼 `cart.php?a=add&pid=N` 这类直链（BOIL 2026 黑五：商家公开说拦了「脚本刷新与直链下单」）。
- 被拦（403）以后不要换 IP 继续冲同一个账号（建议，2026-11-27 待用户确认）：那样更像脚本；停下来，通知用户手动去买。
- **商家可能加 Cloudflare 浏览器验证**（「Just a moment...」，`cf-mitigated: challenge`）：先不登录测一次，区分是验证还是账号被封。
  真 Chromium（单独启动、不用 Playwright 直接启动）能自动通过；拿到的 `cf_clearance` 配同一个 UA、同一个 IP，纯 HTTP 也能用。
  所以浏览器只用来续通行证，要提前续好，别等到抢购时才开浏览器（第一次约 15–25 秒）。
- 走 SSH 隧道时，key 要放行 `challenges.cloudflare.com`，放行后要重启隧道才生效；截图能看出连不上验证服务器。
- TG 推送本身也会慢几秒：有信号时才短时间主动拉频道最新一条，平时只靠推送，并设每天上限（用的是用户自己的账号）。
- 被拉黑以后的出口：走一台可以换 IP 的动态 IP 机器（SSH -D 隧道，key 限定只能转发到目标站点的 443），
  不要用自己的服务依赖这个站点的机器。

## 8. 运维

- 抢购程序作为独立的 systemd 服务或临时 unit 运行，带内存上限。抢完以后：停掉服务，删除账号
  文件和 cookie，提醒用户改密码。**代码和经验都保留**，下次活动接着用。
- SSH 命令被中断后，远端进程可能还在跑。中断后要检查，并停掉残留的进程（2026-11-08 有一个
  被叫停的测试脚本在生产机上继续跑，往购物车里加了商品）。
- 改动生产机之前先备份，部署后检查服务状态和日志。
- **内存要够**（2026-11-28 从 1 GB 的 AWS 搬到 8 核 / 8 GB 的新机器）：三个 Chromium（监控回退、BOIL 续通行证、FAC 抢购）峰值各约 500–700 MB。1 GB 的机器每天换入 swap 约 19 GB，BOIL 续一次通行证要 16–64 秒，搬家后 7 秒。BOIL 抢购的 MemoryMax 从 700M 提到 1200M（新机器上不再被 swap 压着，Chromium 峰值到过 708 MB）。
- **离目标站远一点影响不大**：新机器在洛杉矶，到台湾隧道约 180 ms，每个请求多约 0.2 秒，整单多约 1 秒；跟下单本来的 1 秒间隔、续通行证的时间比，不是瓶颈。
- **搬机器的顺序**：先在新机器装好同版本的 Python 包和 Chromium、起好隧道并核对出口 IP；挑整点以外、抢购没在等货的时候，停掉旧机器（TG 转发要先停），拷整个 `data/`，再在新机器启动。**两台不能同时跑**：同一个 Telegram 用户 session 从两个 IP 同时连会被作废，要用手机验证码重新登录；监控同时跑，请求量也会翻倍。旧机器的服务停用但留着，回滚前要先把新机器最新的 `data/` 拷回去。
- **TG 机器人里改过的扫描间隔会覆盖 config.yaml**（存在 `data/state.json` 的 `settings.provider_intervals`）：改配置里的间隔不生效时，先看这里。
